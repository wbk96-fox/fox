# Atomowy rollback M2→M3 bez stale authorization

Drugi follow-up M3 potwierdza zamknięcie ostatniego P2: rollback nie odczytuje już autoryzacji M3 przed M2, lecz pod mutexem M2 buduje exact failed/LKG pair i przekazuje go do atomowej walidacji M3. `consumeRollbackAndActivate` wymaga enabled-idle, zgodnego pair i braku aktywnego ownera, po czym zachowuje M3 przez trwały swap M2 oraz aktywację; retry, disable i updater mają deterministycznego zwycięzcę. Pakietowy dowód po zmianie obejmuje 12 suites i 114/114 testów bez failures, errors ani skipped. Nie znalazłem nowego P1/P2; pozostają dwa wcześniejsze, non-blocking P3, a **DEVICE RUNTIME NOT VERIFIED**.

**Watch for:** **[P3][confirmed]** journal nadal nie ma fault injection na każdym rename/delete/restore cut-point; **[P3][confirmed]** dokument M3 nadal przypisuje aplikacji ownership optimized output na API 26+.

**Verdict**: APPROVED

**Follow-up decision**: ROOT-CAUSE FIX ACCEPTED

## High-level view

M2 stabilizuje durable selected/previous i tworzy pełne referencje generation/policy/factory. M3 zestawia je z własnym failed/LKG dopiero po zdobyciu swojego mutexu i nie zwalnia go przed zakończeniem swapu oraz aktywacji.

Wszystkie operacje wymagające obu granic idą M2→M3. Retry, updater i rollback konkurują najpierw o M2, disable używa tylko M3, a callback nie reacquire’uje M2 ani selection barrier.

Anulowanie przed M3 nie uruchamia swapu. Po walidacji zwalnia oba mutexy bez publikacji anulowanego ownera; jeśli pointer M2 zdążył przejść na LKG, exact-pair check uniemożliwia ponowne użycie starej autoryzacji.

Trzy kontrolowane wyścigi potwierdzają winner semantics, a statyczny kontrakt zabrania powrotu `rollbackRequest(`. Poza brakiem dowodu device/runtime pozostają wyłącznie wcześniejszy journal cut-point gap i drift dokumentacji ART cache.

## Exact pair jest walidowany dopiero po zdobyciu M2 i M3

`AniyomiLifecycleCoordinator.rollbackFailedActivationAndActivate` zdobywa M2, wykonuje recovery, odczytuje stabilne `selected` i `previous`, a następnie buduje `AniyomiActivationRollbackRequest` z pełnych `AniyomiLoadGenerationRef` (`AniyomiLifecycleCoordinator.kt:84-115`). Produkcyjny scan nie znajduje już symbolu `rollbackRequest`; statyczny test failuje przy każdym powrocie tekstu `rollbackRequest(` i przypina kształt M2→M3 (`AniyomiPackagingContractTest.kt:236-245`).

M3 pobiera swój mutex w `consumeRollbackAndActivate`. Przed callbackiem wymaga jednocześnie `active == null`, `ENABLED_IDLE`, `desiredEnabled`, exact `failedGeneration` i exact `lastKnownGood` (`AniyomiLoadBoundary.kt:86-103`). Mutex pozostaje zajęty podczas `performRollback`, ponownej inspekcji/capability issuance i `activateLocked`; wynik callbacku jest jeszcze porównywany z autoryzowanym LKG. Retry ani disable nie mogą zmienić M3 między checkiem a swapem, a updater nie może zmienić pair pod zajętym M2.

## Jeden kierunek locków daje deterministyczne winner semantics

```text
stage / recover / updater / retry / rollback
                  M2
                   ↓
                  M3 ──→ state / inspection / loader

M3-only: enable / disable / release / process-death recovery
```

Produkcja nie ma wejścia M3→M2. Callback wykonuje prywatne operacje lifecycle pod już posiadanym M2; `selectionChangeAlreadyAuthorized = true` omija reentrant `beforeSelectionChange`, a `selectedGenerationLocked` nie zdobywa mutexu. Disable może więc zakończyć M3, gdy rollback trzyma M2 i czeka na M3, bez cyklu locków.

Test updatera zatrzymuje loader rollbacku przy obu lockach i potwierdza oczekiwanie nowej selekcji do końca exact activation (`AniyomiLoadBoundaryTest.kt:404-485`). Test successful retry publikuje retry przed dopuszczeniem rollbacku i wymaga `ROLLBACK_REJECTED` oraz niezmienionego selected (`:487-555`). Test disable zdobywa M3 przed rollbackiem, kończy `DISABLED` i sprawdza niezmieniony pointer M2 (`:557-635`). Obejmują rollback wygrywający M2 oraz retry/disable unieważniające request przed callbackiem.

## Cancellation nie przywraca starej autoryzacji

`CancellationException` jest ponownie rzucany przez coordinator i boundary. Anulowanie podczas oczekiwania na M3 kończy operację przed callbackiem i zwalnia M2. Po wejściu w callback pojedyncze zapisy korzystają z rollback-backed store; przerwanie pozostawia poprzedni record albo pełną, recoverable fazę `SELECTING`, `CLEANUP_PENDING` lub `SELECTED`, nie częściowy JSON (`AniyomiLifecycleStorage.kt:259-350`).

Jeżeli cancellation nastąpi po trwałym swapie M2, lecz przed aktywacją M3, M2 może pozostać na LKG bez sesji. Stary M3 tuple ma kierunek failed→LKG, podczas gdy następna próba buduje już pair LKG→displaced, więc exact porównanie odrzuca go przed callbackiem. Następne wejście lifecycle wykonuje recovery i reinspekcję; cancellation podczas aktywacji przechodzi przez `cleanupFailedActivation` pod `NonCancellable`, zamyka częściowy loader, czyści legacy workspace i nie publikuje `ACTIVE` (`AniyomiLoadBoundary.kt:191-235,339-399`). Test przerwania realnego konstruktora potwierdza brak sesji, zamknięty handle i usunięty cache (`AniyomiLoadBoundaryTest.kt:196-221`).

Po process death startup najpierw normalizuje M3 bez auto-loadu, potem M2 kończy lub cofa swój journal. Nawet przejściowo starszy idle tuple M3 nie pasuje do requestu budowanego z nowego M2 selected/previous.
