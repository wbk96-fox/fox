# Ścisły łańcuch zależności Gradle i preflighty CI

Zmiana włącza `LockMode.STRICT`, dodaje cztery lockfile’y i metadata SHA-256, koryguje rolę `baselineProfile`, wydziela `androidApis`, przypina wrapper Gradle 8.13 i dodaje preflighty PR/release. Przeliczone hashe i inwentarze zgadzają się z checkpointem: 574/138 stanów aplikacji, 525/51 baseline profile, 135/32 FFmpeg oraz 962 komponenty i 1624 artefakty z pojedynczym SHA-256. Przekazane default/source-mode no-write PASS oraz negatywne testy checksum, missing-lock i bezpośredniego `ExternalModuleDependency` potwierdzają mechanizmy Gradle, ale nie poprawność nowej bramki CI. `lintDebug` nie wykazał błędu supply-chain, lecz zakończył się 3100 errors / 1841 warnings / 26 hints — nie jest to lint PASS ani aprobata release.

Watch for: **P1, confirmed** — workflow używa lenient raportu `dependencies` jako bramki i usuwa jego output; **P1, confirmed** — zmieniony wrapper JAR jest uruchamiany w jobach z sekretami bez wcześniejszej walidacji oficjalnego wrappera.

**Verdict**: NEEDS_CHANGES

## High-level view

Strict mode obejmuje nazwane konfiguracje projektów, lockfile’y zawierają stany puste, `releaseBaselineProfile` pozostaje zapisany po zdezaktywowaniu rozwiązywania agregatu `baselineProfile`, a verification metadata ma dokładnie jeden SHA-256 na artefakt. Negatywne testy dowodzą odrzucenia bezpośredniego braku locka i błędnego checksumu.

Oba workflow uruchamiają raportowy task `dependencies`, który lenientnie przedstawia błędy resolution, nie materializuje wszystkich artefaktów i może zakończyć się sukcesem z węzłami `FAILED`; output jest przekierowany do `/dev/null` (**P1, confirmed**).

Dystrybucja Gradle i bieżący wrapper JAR mają deklarowane poprawne hashe, ale `distributionSha256Sum` działa dopiero po wykonaniu JAR. Workflow nie walidują bootstrapu przed pierwszym `./gradlew`, mimo dostępu jobów do prywatnych properties, danych podpisu i — dla release — `contents: write` (**P1, confirmed**).

Guard `androidApis` odrzuca tylko bezpośredni `ExternalModuleDependency`, pozostawiając inne typy zależności i dowolne lokalne pliki poza lockingiem (**P2, confirmed**). Workflow nie włącza modułu FFmpeg (**P2, confirmed**), a AAPT2, KSP AA i lint są tylko checksum-verified, bez wpisów w lockfile’ach, wbrew deklaracji pełnego lock coverage dla detached configurations (**P2, confirmed**).

Checkpoint poprawnie oddziela supply-chain od czerwonego lint quality gate, lecz błędnie deklaruje LF dla `gradlew.bat`: plik ma 94/94 zakończeń CRLF, bez polityki `.gitattributes`, i powoduje 94 błędy `git diff --check` (**P3, confirmed**).

## Raport `dependencies` nie jest rozstrzygającą bramką

W obu preflightach (`.github/workflows/pr-full-debug-build.yml:49-55`, `.github/workflows/android-release.yml:204-211`) działa **P1 (confirmed)**: `DependencyReportTask` buduje lenient raport. Nierozwiązany komponent lub brak stanu może zostać pokazany jako `FAILED` bez niezerowego exit code, a raport grafu nie wymusza pobrania wszystkich AAR/JAR. `--quiet > /dev/null` usuwa jedyne miejsce, w którym taki błąd byłby widoczny.

```text
CI -> DependencyReportTask -> lenient graph (`FAILED`) -> stdout /dev/null
                                                        -> job może być zielony
```

Negatywne missing-lock i checksum testy dowodzą fail-closed właściwego resolution, nie propagacji błędu przez workflow. Preflight powinien używać dedykowanego taska, który iteruje dozwolone konfiguracje i materializuje nielenientny artifact view/`incoming.artifacts.artifactFiles`; test CI powinien wymagać niezerowego exit code po kontrolowanym usunięciu stanu i zmianie checksumu.

## Wrapper JAR pozostaje niezaufanym bootstrapem

SHA-256 `gradle/wrapper/gradle-wrapper.jar` wynosi `81a82aaea5abcc8ff68b3dfcb58b3c3c429378efd98e7433460610fecd7ae45f`, a `gradle/wrapper/gradle-wrapper.properties:3-4` wskazuje Gradle 8.13 z checksumem dystrybucji `20f1b117…ed78`. **P1 (confirmed)** wynika z braku `wrapper-validation` lub niezależnego sprawdzenia JAR przed wykonaniem zmienionego binarnego bootstrapu; checksum dystrybucji nie uwierzytelnia kodu, który go odczytuje.

Wrapper PR ma dostęp do sekretów używanych do properties, a release definiuje sekrety na poziomie joba i ma `contents: write`. Walidację oficjalnego wrappera, przypiętą do przejrzanego immutable SHA akcji, trzeba wykonać bezpośrednio po checkout i przed każdym `./gradlew`; sekrety należy ograniczyć do kroków, które ich potrzebują.

## `androidApis` wyłącza lock szerzej niż deklaruje kontrakt

`build.gradle.kts:32-45` wyłącza locking dla każdej konfiguracji nazwanej `androidApis`, po czym filtruje tylko `ExternalModuleDependency`. **P2 (confirmed)**: `ProjectDependency` z tranzytywnymi modułami, inne self-resolving dependency i dowolny `FileCollectionDependency` przejdą warunek, choć całe resolution jest poza lockiem. Nie ma też walidacji kanonicznego `${sdk}/platforms/android-36/android.jar`.

Test z `junit:junit:4.13.2` obejmuje wyłącznie filtrowany typ. Wyjątek trzeba ograniczyć do oczekiwanych projektów AGP i dokładnie zweryfikowanego pliku SDK, odrzucając `extendsFrom`, constraints i project dependencies; testy powinny dodać projektową zależność tranzytywną oraz obcy lokalny JAR.

## Warunkowy lock FFmpeg nie ma konsumenta CI

`settings.gradle.kts:41-53` dołącza `:ffmpeg-decoder-downmix` tylko dla `useLocalFfmpegDecoder`; workflow nie ustawia tej właściwości ani wymaganych katalogów. **P2 (confirmed)**: lockfile FFmpeg może zniknąć lub rozjechać się, a oba workflow nadal sprawdzą tylko graf domyślny. Przekazany source-mode no-write PASS jest dowodem snapshotu, nie stałą bramką regresji.

Należy dodać job przygotowujący przypięte źródło/build FFmpeg i uruchamiający fail-hard resolver z `-PuseLocalFfmpegDecoder=true`, albo rozdzielić dołączenie modułu do audytu grafu od kosztownego native builda.

## Detached tool artifacts mają checksumy, lecz nie lock state

Żaden lockfile nie zawiera AAPT2 `8.13.2-14304508`, `symbol-processing-aa-embeddable:2.3.12`, lint `31.13.2` ani stanu `detachedConfiguration`; komponenty występują tylko w `gradle/verification-metadata.xml:2215-2229`, `2407-2437`, `2965-2971`. To **P2 (confirmed)** wobec deklaracji `.kiro/FOX_IMPLEMENTATION_STATE.md:837-840`, że lock obejmuje cały realny graph wraz z detached configurations.

Dependency verification chroni bajty znanych koordynatów, ale nie jest version selection lockiem. Checkpoint musi rozdzielić „locked named project configurations” od „checksum-verified detached/plugin tooling”; pełny pin wymaga nazwanych lockowalnych konfiguracji albo osobnego manifestu oczekiwanych koordynatów z testem driftu.

## Checkpoint błędnie opisuje EOL skryptu Windows

`.kiro/FOX_IMPLEMENTATION_STATE.md:815-817` deklaruje LF, lecz każdy z 94 wierszy `gradlew.bat` kończy się CRLF. Bez polityki `*.bat` w `.gitattributes`, `git diff --check` zgłasza 94 błędy trailing whitespace (**P3, confirmed**).

Należy rzeczywiście zapisać LF albo świadomie zachować CRLF, dodać deterministyczną politykę `.gitattributes` i poprawić checkpoint.
