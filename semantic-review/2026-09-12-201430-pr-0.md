## High-level view

Zewnętrzny pipeline jest fail-closed: wejściowy URL, redirect destination, zagnieżdżone listy i `.cs3` muszą pozostać na HTTPS. Effective response URL jest bazą kolejnego rozwiązania, więc cleartext trust path i redirect-relative base są zamknięte.

Niekompletna lista, aktywny invalid entry lub niejednoznaczny duplikat blokują generację. Wszystkie artefakty są stagingowane przed aktywacją; failure lub cancellation przed metadata commit odtwarza poprzednie pliki, a stale cleanup następuje po commicie. Ten mutex nie obejmuje jednak add/refresh JS zapisujących ten sam pełny dokument scraperów (**confirmed, P1 blocker**).

Providery i extractory mają identity-based ownership z ochroną built-ins i shared owners. Per-owner/global disable utrwala stan przed unloadem, usuwa owned globals i blokuje lazy reload.

Poprawki `CancellationException` zachowują propagację callera. Single-flight odróżnia ją od anulowania współdzielonego child job po disable przez sprawdzenie aktywności bieżącego kontekstu.

### 1. Cleartext executable metadata — RESOLVED, remaining severity: none

`ExternalRepoParser.fetchDocument` odrzuca nie-HTTPS przed requestem i sprawdza `response.request.url` przed body (`ExternalRepoParser.kt:211-256`). `resolveHttpsUrl` wymusza HTTPS po RFC resolution dla `pluginLists`, artefaktu i `repositoryUrl` (`ExternalRepositoryContract.kt:52-57,108-137`), a loader niezależnie sprawdza wejściowy i finalny URL `.cs3` przy wyłączonym SSL downgrade (`ExternalExtensionLoader.kt:270-289`). TLS `MockWebServer` tests potwierdzają brak requestu dla initial HTTP oraz do targetów HTTPS→HTTP zarówno dla metadata, jak i artefaktu (`ExternalRepoParserTest`, `ExternalExtensionLoaderLifecycleTest`).

### 2. Rejected active update becoming stale deletion — RESOLVED, remaining severity: none

`isAuthoritativeForRemoval` wymaga kompletności wszystkich list oraz braku active-invalid i duplicate ambiguity (`ExternalRepoParser.kt:31-43`). Jawnie inactive entry może autoryzować usunięcie, lecz aktywny nieweryfikowalny wpis blokuje całą generację (`ExternalRepositoryContract.kt:60-106`, `ExternalRepoParser.kt:136-180`). Manager odrzuca taki refresh przed synchronizatorem, który ma dodatkowy invariant `check` (`PluginManager.kt:624-655`; `ExternalRepositorySynchronizer.kt:54-64`). Testy obejmują incomplete list, invalid active metadata, duplicate ambiguity i brak synchronizacji/deletion po odrzuconym refreshu.

### 3. Unserialized, non-transactional activation — PARTIALLY RESOLVED, remaining severity: P1

Synchronizator staginguje wszystkie wpisy i przy pojedynczym failure nie aktywuje żadnego (`ExternalRepositorySynchronizer.kt:64-89,115-146`). `activateAndCommit` zachowuje backupy, cofa wszystkie aktywacje po exception/cancellation przed commit point i finalizuje je dopiero po nieprzerywalnym metadata commit (`ExternalPluginLifecycleCoordinator.kt:29-73`). Repository descriptor i kompletna lista scraperów trafiają do jednego `DataStore.edit` (`PluginDataStore.kt:156-189`), a stale files są usuwane dopiero później (`ExternalRepositorySynchronizer.kt:91-97,201-228`). Add/refresh/remove DEX oraz disable współdzielą singletonowy coordinator (`PluginManager.kt:431-503,593-600,663-716`), zamykając pierwotne interleavingi DEX, aggregate-stage failure i metadata rollback.

Pozostaje **confirmed, P1 blocker**. `downloadJsScrapers` czyta pełny snapshot przed requestami i na końcu zastępuje nim całą listę (`PluginManager.kt:1083-1176`), ale add JS (`PluginManager.kt:404-425`) i JS branch refreshu (`PluginManager.kt:588-616`) działają poza `externalPluginLifecycle.serialized`. Jeśli JS zrobi snapshot, DEX zatwierdzi nowy artifact+metadata, a JS zapisze później, wraca stara metadata DEX; w odwrotnej kolejności DEX gubi świeżą zmianę JS. Serializacja pojedynczych `DataStore.edit` nie zapobiega temu lost update.

Wymagany jest wspólny lock dla wszystkich full-list writerów albo repository-scoped merge wewnątrz `DataStore.edit`. Obecny gate testuje DEX-refresh-vs-disable i lokalny rollback, nie DEX generation vs równoległy add/refresh JS.

### 4. Provider mappings surviving cleanup — RESOLVED, remaining severity: none

`CloudstreamProviderRegistry` snapshotuje identity union `APIHolder.allProviders`/`apis`, przypisuje ownerów w `IdentityHashMap`, a po ostatnim ownerze wywołuje `removePluginMapping` i usuwa tę samą identity z `allProviders` (`CloudstreamProviderRegistry.kt:14-101`). Loader claimuje lub wycofuje dokładne delta registrations wokół load/preload/validation (`ExternalExtensionLoader.kt:382-533,574-684,734-802,861-894`). Testy na rzeczywistych globals sprawdzają `allProviders`, `apis`, przebudowę `apiMap`, ochronę built-in identity i shared owner lifecycle.

### 5. Same-mainUrl extractor identity leak — RESOLVED, remaining severity: none

`ExternalExtractorRegistry` używa `IdentityHashMap` oraz `===`, więc różne instancje o tym samym `mainUrl` mają osobny lifecycle, a współdzielona instancja znika dopiero po ostatnim ownerze (`ExternalExtractorRegistry.kt:18-88`). Testy obejmują dwie foreign identities o jednym URL, built-in/external z tym samym URL i shared exact identity (`ExternalExtractorRegistryTest`, `ExternalExtensionLoaderLifecycleTest`).

### 6. Disable leaving globally registered code reachable — RESOLVED, remaining severity: none

Per-owner, per-repository i global toggles są serializowane, używają persistence jako commit point i nie unloadują po odrzuconym zapisie (`PluginManager.kt:663-716`). Po commicie loader oznacza ownera disabled, evictuje API/classloader/preload cache, wyrejestrowuje owned identities i blokuje ponowny load; global enable pozostaje lazy (`ExternalExtensionLoader.kt:813-849`). Execution/preload filtrują `enabled && manifestEnabled`, a disable anuluje matching in-flight jobs (`PluginManager.kt:292-298,718-725,744-769,842-900`). Testy potwierdzają persist-before-unload, rejected-write no-op, manifest gate, shared identity, global unload i lazy re-enable.

### 7. Redirect-relative URL base remaining stale — RESOLVED, remaining severity: none

Fetch zwraca body z `response.request.url`; manifest rozwiązuje listy względem effective repo URL, a plugin entries względem effective list URL (`ExternalRepoParser.kt:46-49,79-100,194-207,237-253`). Test z dwoma redirectami sprawdza cztery request paths oraz końcowe artifact/repository URLs (`ExternalRepoParserTest:29-93`).

### CancellationException regression check

`PluginManager` jawnie rethrowuje cancellation z add/refresh, streaming, JS/DEX execution, diagnostics i download. W single-flight handler `currentCoroutineContext().ensureActive()` propaguje anulowanie callera, ale aktywnemu callerowi pozwala zwrócić pusty wynik, gdy współdzielony deferred anulował disable (`PluginManager.kt:849-879`). `ExternalExtensionRunner` rethrowuje cancellation przed szerokimi handlerami w search/load/loadLinks; jego lokalny timeout nadal może zwrócić częściowe linki. Dwa runner tests potwierdzają propagation w normalnym i diagnostycznym flow, a coordinator test łączy propagation z rollbackiem. Nie stwierdzono regresu semantycznego.
