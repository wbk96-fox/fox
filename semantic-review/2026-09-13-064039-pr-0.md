# Atomowe zużycie rollback authorization M2→M3 w Aniyomi

Finalny statyczny follow-up potwierdza usunięcie root cause ostatniego P2: rollback nie pobiera już autoryzacji M3 przed zdobyciem M2, lecz tworzy exact M2 pair i waliduje ją pod M3 przed zmianą pointera. Oba mutexy pozostają zajęte przez swap oraz aktywację exact LKG, więc retry, updater i `disable()` nie mogą wykorzystać stale failed/LKG pair. Analiza lock order, anulowania i stanów częściowych nie ujawniła nowego P1/P2; dostarczony przez użytkownika gate ma `compileDebugKotlin` i `compileDebugUnitTestKotlin` BUILD SUCCESSFUL oraz 12 suites / 114 tests / 0 failures / 0 errors / 0 skipped, ale nie był ponownie uruchamiany w tym statycznym review. Pozostają dwa jawnie non-blocking P3; **DEVICE RUNTIME NOT VERIFIED**.

**Watch for:** **[P3][confirmed]** `LOAD_BOUNDARY_DESIGN.md` nie opisuje jeszcze nowego callbacku pod M2→M3 i nadal przypisuje M3 platform-managed ART output; **[P3][confirmed]** M3 journal nadal nie ma fault injection na każdym rename/delete/restore cut-point.

## High-level view

Rollback zaczyna teraz pod M2 od aktualnych `selected` i `previous`, z których powstaje exact failed/LKG tuple obejmujący generation, policy i factory identity. M3 odrzuca wszystko poza enabled-idle, bez active ownera i z identycznym durable pair, po czym pozostaje zajęty przez pointer swap i aktywację.

Callback wykonuje lifecycle transaction pod już posiadanym M2 i omija ponowne wejście w selection barrier M3. Pozostałe ścieżki dwulockowe także zachowują M2→M3, natomiast `disable()` używa tylko M3; prześledzony wait-for graph nie zawiera cyklu.

Anulowanie może pozostawić wyłącznie recovery-aware fazę M2/M3 albo M2 już przełączone z F/G na G/F przy starym, fail-closed M3 F/G. Testy obejmują rollback kontra updater, zwycięski retry i `disable()` oraz statyczny zakaz `rollbackRequest()`; granicą dowodu nadal są JVM/static, nie device runtime.

## Exact failed/LKG pair jest konsumowany dopiero pod M2

`rollbackAfterFailedActivation()` deleguje bez wcześniejszego odczytu M3 do `rollbackFailedActivationAndActivate()` (`AniyomiLoadBoundary.kt:663-679`). Lifecycle zdobywa M2, wykonuje recovery, odczytuje aktualne `selected` i `previous`, a następnie buduje `AniyomiActivationRollbackRequest` (`AniyomiLifecycleCoordinator.kt:85-115`). Oba pola są `AniyomiLoadGenerationRef`, którego equality obejmuje SHA/generation ID, policy ID, policy version i factory class (`AniyomiLoadBoundaryModels.kt:26-31`). Scan nie znalazł produkcyjnego `rollbackRequest()`; jedyne wystąpienie jest negatywną asercją kontraktową.

`consumeRollbackAndActivate()` zdobywa M3 po M2 i wymaga braku active ownera, `ENABLED_IDLE`, `desiredEnabled=true` oraz exact equality durable `failedGeneration` i `lastKnownGood` z requestem (`AniyomiLoadBoundary.kt:87-104`). Callback wykonuje `performRollback(..., selectionChangeAlreadyAuthorized=true)`, tworzy świeżą capability z wybranego artefaktu, a M3 sprawdza, czy zwrócony target nadal jest exact LKG przed `activateLocked` (`AniyomiLifecycleCoordinator.kt:115-130`; `AniyomiLoadBoundary.kt:104-112`).

```text
M2 lock
  recover + read selected F / previous G
  build exact request F/G
  M3 lock
    require enabled-idle + no active + durable F/G
    M2 callback: inspect G -> pointer G/F -> inspect/capability G
    require returned ref == G
    activate G
  release M3
release M2
```

Usunięta luka `M3 read → release M3 → wait M2` nie ma równoważnej ścieżki: swap nie zaczyna się przed bieżącą walidacją M3, a request nie opuszcza stacku operacji.

## Retry, disable i updater zachowują acykliczny porządek

Activation, explicit rollback, updater/stage transition, recovery transition i zwykły rollback zaczynają od lifecycle M2, a następnie wchodzą w M3 przez activation albo selection barrier. `consumeRollbackAndActivate` nie zdobywa M2 od środka; callback działa pod M2 już posiadanym przez caller. `selectionChangeAlreadyAuthorized=true` zapisuje M2 transition bez ponownego `beforeSelectionChange`, eliminując self-deadlock na niereentrantnym M3 (`AniyomiLifecycleCoordinator.kt:115-121,502-531`). Startup recovery i `enableAndActivate()` używają locków sekwencyjnie, a `disable()` nie wchodzi do lifecycle.

Retry wygrywający M2/M3 publikuje active F, więc późniejszy rollback zostaje odrzucony przez `active != null` przed callbackiem. `disable()` wygrywający M3 pozostawia rollback czekający z M2, po czym walidacja widzi `DISABLED` i nie zmienia M2. Rollback wygrywający oba locki blokuje updater/retry na M2 i `disable()` na M3 do końca swapu oraz aktywacji; po zwolnieniu każda operacja wykonuje aktualną walidację. Nie ma krawędzi wait-for M3→M2.

Deterministyczne testy pokrywają te rozstrzygnięcia: updater czeka na exact rollback activation (`AniyomiLoadBoundaryTest.kt:404-484`), udany retry powoduje `ROLLBACK_REJECTED` bez cofnięcia pointera (`:487-555`), a `disable()` powoduje odrzucenie bez zmiany M2 (`:557-635`). `AniyomiPackagingContractTest` pilnuje M2-held handoff, callbacku z `selectionChangeAlreadyAuthorized=true` oraz braku `rollbackRequest()` w produkcji (`AniyomiPackagingContractTest.kt:205-246`).

## Anulowanie pozostawia recovery-aware, fail-closed state

Anulowanie podczas oczekiwania na mutex nie zmienia M2 ani M3. W callbacku write lifecycle jest rollback-backed; przerwanie write próbuje przywrócić `.bak`, a trwałe `SELECTING` i `CLEANUP_PENDING` są obsługiwane przez `recoverLocked` (`AniyomiLifecycleStorage.kt:258-327`; `AniyomiLifecycleCoordinator.kt:303-421,502-535`). Jeśli M2 zdąży przejść z F/G na G/F przed aktywacją, pozostawione M3 F/G nie może zatwierdzić następnego requestu G/F; normalna `activateSelected()` może natomiast podjąć G.

Podczas loader/cache work anulowanie zamyka częściowy handle i legacy workspace pod `NonCancellable`, nie publikuje active ownera i wraca do idle z nowym failed target (`AniyomiLoadBoundary.kt:171-273,398-456`). Przerwanie przy zapisie `ACTIVATING` przed utworzeniem zasobów pozostawia fazę normalizowaną przez `normalizeStaleRecordIfNecessary()` lub startup recovery. Te cut-pointy nie odtwarzają F/G jako authority dla odwróconego pointera M2.
