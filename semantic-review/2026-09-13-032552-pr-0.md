# Controlled Aniyomi classloader ownership and M2→M3 load boundary

M3 adds a single-owner boundary around the M2-selected Aniyomi generation: M2 reinspects and pins the selection, then M3 opens a strict child loader, constructs the parent-typed factory, journals publication, and releases ownership before pointer changes. The normal path follows the intended M2→M3 lock order, and the tests load real isolated JVM class bytes rather than returning fabricated success. Three **confirmed** blocking gaps remain in Android writable-DCL handling, asynchronous startup recovery, and policy-aware selection changes; rollback/cache issues are **confirmed**, while ambient TCCL escape is **likely**. **Watch for:** **confirmed** writable `extension.apk` rejection on modern Android, **confirmed** orphan/duplicate ownership when startup recovery loses a race with activation, and **confirmed** stale ownership when the SHA stays constant but the policy tuple changes.

## High-level view

`AniyomiLifecycleCoordinator.activateSelected` keeps M2 locked through exact policy lookup, fresh inspection, capability creation, and M3 activation. No lock inversion was found: dual-lock flows enter M2 before M3, and the rollback facade releases its M3 read before acquiring M2. **Confirmed:** the selection barrier nevertheless reduces the selected identity to a SHA string, weaker than the full identity used for duplicate-owner checks.

The source and cache resolvers reject static traversal/symlink layouts and use app-private roots. **Confirmed:** the published generation remains writable, conflicting with target-SDK-36 DCL enforcement and preserving a mutation window; `DexClassLoader` also ignores the claimed generation-specific optimized directory from API 26 onward.

Reflection is limited to the freshly reported public no-arg constructor, with exact child-loader and parent-interface checks. **Likely:** construction on an un-rebound pooled thread lets TCCL-based APIs bypass the intended ambient-classpath restriction even though direct child resolution cannot fall back to the app loader.

Fresh-instance process-death recovery does not auto-load code. **Confirmed:** asynchronous startup does not gate activation, so recovery can drop a newly published live session without closing it. Explicit rollback is also split across separately locked calls and can activate a generation other than the validated rollback target.

Existing XML artifacts record 20/20 load-boundary, 4/4 storage, and 6/6 packaging/static-guard tests; they were not rerun during this read-only review. They cover JVM `URLClassLoader`, not Android `DexClassLoader`, target-SDK writable-code enforcement, or ART cache placement. **DEVICE EXECUTION NOT VERIFIED** is not counted as a code finding.

<summary>Issues (7)</summary>

1. **[P1][confirmed] Policy-only pointer swaps bypass release** — the barrier compares only `generationId`, so the selected policy tuple can change while the old-policy factory remains active. Pass and compare the full immutable generation/policy/factory identity.
2. **[P1][confirmed] Writable APK reaches `DexClassLoader`** — the target-SDK-36 generation remains writable, which Android 14+ rejects and older Android leaves mutable between inspection and load. Publish read-only-before-write and verify permissions immediately before opening the loader.
3. **[P1][confirmed] Startup recovery can orphan an active loader** — unawaited recovery sets `active = null` without closing a session that may have won the startup race. Gate M3 APIs on one-time recovery and handle a non-null owner safely.
4. **[P2][confirmed] Rollback target is not pinned through activation** — failed/LKG read, M2 swap, and activation are separate operations, allowing a retry or updater to change the meaning/result. Perform validation, swap, capability issuance, and activation under one M2-pinned orchestration.
5. **[P2][likely] Worker TCCL exposes ambient app classes** — construction does not replace the pooled thread's application classloader, so TCCL consumers can bypass direct routing. Bind/restore TCCL around construction and test `ServiceLoader`/TCCL access.
6. **[P2][confirmed] Claimed optimized-cache ownership is ineffective on API 26+** — Android ignores `DexClassLoader.optimizedDirectory`, so cleanup removes a marker rather than ART output. Align release/recovery claims with platform-managed caching or use a supported mechanism.
7. **[P3][confirmed] Journal rollback cut points are untested** — storage tests synthesize one interrupted layout but do not inject rename/delete/restore failures. Add fault-injectable filesystem tests for every persistence transition.

## Policy-aware ownership is lost at the selection barrier

**[P1][confirmed]** M3's active owner is keyed by the complete `AniyomiLoadGenerationRef`—generation, policy ID/version, and factory class—and duplicate activation compares that complete value (`AniyomiLoadBoundary.kt:133`; `AniyomiLoadBoundaryModels.kt:26-31`). The pointer-change contract passes only `currentGenerationId` and `nextGenerationId`, and both coordinator and boundary return early when those hashes match (`AniyomiLifecycleCoordinator.kt:743-748`; `AniyomiLoadBoundary.kt:96-105`).

A policy rollout can repin the same bytes under a new policy version. M2 then changes its authoritative tuple without invoking M3 release: the old-policy factory remains active while the journal points at the new policy, and later activation fails as `DUPLICATE_OWNER`. Pass full immutable refs through the barrier, compare exact tuples, and add a same-SHA/different-policy update and rollback test. The generation-only displacement checks at `AniyomiLifecycleCoordinator.kt:202-205` and `:329-332` need the same correction.

## Writable generation cannot satisfy the Android DCL contract

**[P1][confirmed]** The transaction candidate is created through `FileOutputStream`, then publication only renames it into `generations/<sha>/extension.apk` (`AniyomiLifecycleStorage.kt:399-402,447-472`). Neither publication nor `AndroidAniyomiClassLoaderFactory.open` marks or verifies the source read-only before constructing `DexClassLoader` (`AniyomiClassLoader.kt:24-40`). With `targetSdk = 36` (`app/build.gradle.kts:169-172`), Android 14+ rejects the writable APK/DEX; older releases retain a TOCTOU window between the fresh hash and path-based loader open.

Publish the generation with the platform-safe create/open-FD/mark-read-only/write/fsync sequence, reject or migrate reused writable generations, and recheck read-only status immediately before load. The JVM fixture creates ordinary writable files and cannot catch this Android failure.

**[P2][confirmed]** The design deletes `codeCacheDir/aniyomi_extensions/<generationId>` as if it owns optimized output. Production passes that path to `DexClassLoader` (`AniyomiClassLoader.kt:85-94`), but the installed API-37 SDK contract says `optimizedDirectory` has no effect since API 26 (`dalvik/system/DexClassLoader.java`). On modern devices the deleted directory is a marker, not ART's optimized-artifact location. Redefine this as logical source ownership under platform-managed ART caching, or use a supported mechanism; release/recovery must not claim physical optimized-code removal on API 26+.

## Asynchronous startup recovery can orphan a live loader

**[P1][confirmed]** `AniyomiLifecycleStartup.start` launches recovery on an unawaited IO scope (`AniyomiLifecycleCoordinator.kt:793-798`). `recoverAfterProcessDeathLocked` unconditionally assigns `active = null` and clears cache state without closing a current handle (`AniyomiLoadBoundary.kt:502-505`). The recovery test uses only a fresh boundary after simulated death (`AniyomiLoadBoundaryTest.kt:452-490`).

If activation publishes before the startup coroutine reaches M3, recovery erases the in-memory owner, normalizes durable `ACTIVE` to idle, and leaves the old loader unclosed; another activation can then publish a second owner. Add an awaited one-time startup barrier before exposing M3 operations, reject or safely release a non-null live owner in recovery, and cover the activation-wins-startup ordering deterministically.

## Worker TCCL bypasses strict loader routing

**[P2][likely]** Factory construction runs in `runInterruptible(Dispatchers.IO)` without rebinding/restoring `Thread.currentThread().contextClassLoader` (`AniyomiLoadBoundary.kt:171-178`). Android coroutine workers normally carry the application `PathClassLoader`, so child code using `ServiceLoader`, TCCL resource lookup, or `contextClassLoader.loadClass` can see ambient FOX.TV classes despite `StrictAniyomiDexClassLoader` rejecting ordinary out-of-allowlist resolution (`AniyomiClassLoader.kt:72-121`).

The fixture tests only caller-loader `Class.forName("com.foxtv.app.FoxTvApplication")` (`AniyomiLoadBoundaryTestFixtures.kt:169-173`), not TCCL. Bind TCCL to the owned strict loader during construction, restore it in `finally`, and add a TCCL/`ServiceLoader` escape test. This remains classpath hygiene, not a sandbox claim.

## Failed-activation rollback is not one pinned operation

**[P2][confirmed]** `rollbackAfterFailedActivation` reads the M3 failed/LKG pair, releases M3, performs the M2 pointer rollback, releases M2, then reacquires M2→M3 in a separate `activateSelected` call (`AniyomiLoadBoundary.kt:608-618`). A retry can make the request stale before swap, or updater C can replace rolled-back A before activation, causing the rollback method to return C.

Validate/consume the request, validate M2 selected/previous, swap the pointer, issue the fresh capability, and activate the rollback target in one M2-pinned orchestration that acquires M3 only in legal order. Add retry-, disable-, and update-vs-rollback races; return the validated `lastKnownGood` generation or a typed stale-operation failure.

## Load-journal fault coverage stops at one synthetic cut point

**[P3][confirmed]** `AniyomiLoadBoundaryStorageTest` manually creates one `base + .bak + .next` interrupted-promotion layout (`AniyomiLoadBoundaryStorageTest.kt:19-39`), but does not inject failure/cancellation at the rename, delete, and restore branches in `FileAniyomiLoadBoundaryStateStore.write/rollbackWrite` (`AniyomiLoadBoundaryStorage.kt:62-151`). Add a fault-injectable file-operations seam and verify every cut point leaves the old valid record or a recoverable staged layout. This is a coverage gap, not a demonstrated corruption bug.

The JVM archive contains separate controlled DEX and `.class` representations; ART never executes that DEX in these tests. Existing results therefore do not resolve writable-DCL, ART-cache, Android-TCCL, or startup-scheduling findings. No full build, lint, release build, or device execution was run, as requested.
