## High-level view

Pełny zapis JS nadal trzyma lokalny snapshot przez czas pobierania kodu, ale snapshot i końcowe `saveScrapers` są teraz jedną sekcją krytyczną wspólną z planowaniem i commitem DEX. Drugi writer pobiera stan dopiero po zakończeniu poprzedniej generacji.

`addFoxTvRepository` i JS branch `refreshRepository` wchodzą do `serialized` dokładnie raz. `downloadJsScrapers` nie przejmuje mutexa ponownie, a DEX-owy `activateAndCommit` jest helperem commitowym bez drugiego `withLock`, więc poprawka nie tworzy reentrancy ani cyklu locków.

Test blokuje DEX wewnątrz wspólnej sekcji, uruchamia refresh JS i sprawdza brak requestu JS przed zwolnieniem DEX oraz zachowanie nowej generacji DEX w finalnym pełnym zapisie JS. Wszystkie siedem pierwotnych findings ma status RESOLVED.

### Jeden lifecycle mutex obejmuje oba pełne writery JS

`addFoxTvRepository` obejmuje `dataStore.addRepository` i `downloadJsScrapers` jednym `externalPluginLifecycle.serialized` (`PluginManager.kt:406-426`). JS branch `refreshRepository` ponownie odczytuje repozytorium, pobiera manifest, aktualizuje descriptor i wywołuje `downloadJsScrapers` wewnątrz pojedynczej sekcji `serialized` (`PluginManager.kt:601-617`). Są to jedyne dwa wywołania prywatnego `downloadJsScrapers` (`PluginManager.kt:421,613`), więc żaden produkcyjny call site nie wykonuje tego full-list read-modify-write poza koordynatorem.

Operacje DEX add/refresh korzystają z tej samej wstrzykniętej instancji `ExternalPluginLifecycleCoordinator`; klasa jest `@Singleton`, a `ExternalRepositorySynchronizer.synchronizeLocked` zakłada lock callera i wywołuje helper `activateAndCommit` bez ponownego `withLock` (`ExternalPluginLifecycleCoordinator.kt:18-30`; `ExternalRepositorySynchronizer.kt:54-55,201-207`). Gdy DEX kończy pierwszy, JS wykonuje `dataStore.scrapers.first()` po jego commicie. Gdy JS kończy pierwszy, plan DEX powstaje z zapisanego stanu JS. Stary snapshot nie może nakładać się na commit drugiego writera.

### Brak niereentrantnej ścieżki i deadlocku

`serialized` używa pojedynczego `Mutex.withLock` (`ExternalPluginLifecycleCoordinator.kt:19-24`), ale nowy call graph nie zagnieżdża tej operacji: add/autodetection dochodzi do `addFoxTvRepository` bez lifecycle locka, JS refresh przejmuje go tylko w swoim branchu, a `downloadJsScrapers` nie odwołuje się do koordynatora. DEX synchronizer wywołuje `activateAndCommit`, nie `serialized`, z wnętrza sekcji chronionej przez managera.

`triggerRemoteSync` z add path tylko planuje osobną coroutine i nie oczekuje na operację wracającą do lifecycle locka. Nie znaleziono reentrancy ani odwrócenia kolejności locków w ocenianych ścieżkach.

### Test dowodzi kolejności i zachowania obu generacji

Test `DEX generation and JS refresh cannot overwrite each other` zatrzymuje mock synchronizatora po wejściu DEX do lifecycle section, po czym uruchamia JS refresh (`PluginManagerExternalLifecycleTest.kt:152-216`). Serwer nie otrzymuje requestu manifestu JS przed zwolnieniem DEX (`:217-225`), ponieważ fetch jest już wewnątrz tego samego mutexa. Po `releaseDex` test wymaga sukcesu obu operacji, dokładnie trzech requestów JS oraz pełnego zapisu zawierającego nowy wpis JS i wersję `2` generacji DEX (`:226-231`). Writer z dawnym snapshotem zachowałby wersję `1`, więc finalna asercja bezpośrednio wykrywa wcześniejszy lost update.

Dynamiczny scenariusz obejmuje refresh; add jest potwierdzony statycznie przez jedyne drugie wywołanie tego samego writera wewnątrz tego samego koordynatora.
