# Domknięcie ownership M3 z nieatomowym żądaniem rollbacku

Follow-up potwierdza zamknięcie trzech wcześniejszych P1: selection barrier przenosi generation/policy/factory identity, APK staje się read-only przed pierwszym zapisem i jest sprawdzany przed `DexClassLoader`, a awaited startup gate nie pozwala aktywacji wyprzedzić recovery ani zgubić zgodnego live ownera. TCCL jest związany ze strict child loaderem, a M2 utrzymuje mutex przez rollback pointer swap i aktywację; świeży gate M3 zakończył się wynikiem 42/42. Pozostaje jeden **[P2][confirmed]**: request pobrany pod M3 nie jest atomowo walidowany ani konsumowany po zdobyciu M2, więc udany retry lub `disable()` może zostać cofnięty przez stale rollback. Dwa **[P3][confirmed]** są non-blocking: brak journal cut-point fault injection i stary opis ownership optimized output na API 26+; **DEVICE RUNTIME NOT VERIFIED**.

**Watch for:** **[P2][confirmed]** retry/disable może unieważnić M3 pair między `rollbackRequest()` a M2 swap; **[P3][confirmed]** journal ma tylko syntetyczny interrupted layout; **[P3][confirmed]** `LOAD_BOUNDARY_DESIGN.md` nadal przypisuje M3 usuwanie platform-managed ART output.

**Verdict**: NEEDS_CHANGES

**Release decision**: CHANGES REQUIRED

## High-level view

M2 i M3 porównują teraz `AniyomiLoadGenerationRef` zawierający SHA, policy ID/version i factory class. Regresja same-SHA/different-policy zmienia policy version przy identycznych bajtach i potwierdza release starego ownera przed nową aktywacją.

Publikacja stosuje wzorzec Android DCL: odbiera ścieżce writable mode po otwarciu nowego output FD, lecz przed pierwszym `write`, zachowuje go po rename i sprawdza ponownie przy loaderze. Dowody obejmują kod, filesystem JVM i static contract, nie ART na urządzeniu.

Jednorazowe recovery jest współdzielonym gate’em wszystkich obecnych produkcyjnych operacji M3, a exact live `ACTIVE/sessionId/target` jest zachowywany. Konstruktor factory działa z owned child TCCL i przywraca poprzedni loader.

Rollback jest przypięty pod M2 od walidacji selected/previous do końca activation, co serializuje updater. Wcześniejszy odczyt M3 nie jest jednak przypięty: retry lub disable może zmienić M3 bez zmiany M2 pair i stale request nadal zostanie wykonany.

Kod rozróżnia writable legacy directory z API 24–25 od ignorowanego argumentu i platform-managed ART cache od API 26. Dokument projektu zachował stary model ownership, a journal tests nadal nie wstrzykują awarii rename/delete/restore.

## Exact identity i immutable DCL source

`AniyomiLoadGenerationRef` obejmuje `generationId`, `policyId`, `policyVersion` i `factoryClassName` (`AniyomiLoadBoundaryModels.kt:26-33`). `commitSelectionTransition` tworzy ten ref dla current i next (`AniyomiLifecycleCoordinator.kt:777-782`), a M3 porównuje go z aktywnym ownerem (`AniyomiLoadBoundary.kt:96-116`). Pozostałe artifact fields są ponownie wiązane z exact host policy przed handoff. Test same-SHA/different-policy zamyka stary owner, pozostawia boundary idle po swapie i dopiero potem aktywuje nowy policy ref (`AniyomiLoadBoundaryTest.kt:371-402`). Poprzedni identity P1 jest zamknięty.

`copyCapabilityToTransaction` otwiera `FileOutputStream`, wykonuje `setReadOnly()` i sprawdza `!canWrite()` przed pierwszym buforem (`AniyomiLifecycleStorage.kt:413-432`). Publication odrzuca writable candidate/reused generation i kontroluje destination po rename (`AniyomiLifecycleStorage.kt:476-495`); `AndroidAniyomiClassLoaderFactory.open` ponawia canonical/read-only check przed strict loaderem (`AniyomiClassLoader.kt:24-60`). Storage i packaging tests potwierdzają mode oraz kolejność. Poprzedni writable-source P1 jest zamknięty na poziomie kodu/JVM; **DEVICE RUNTIME NOT VERIFIED**.

## Awaited recovery i strict constructor TCCL

`AniyomiLifecycleStartup` publikuje jednokrotny wynik przez `CompletableDeferred`, a każda operacja `AniyomiLoadCoordinator` czeka na `startup.awaitReady()` (`AniyomiLifecycleCoordinator.kt:839-878`; `AniyomiLoadBoundary.kt:614-666`). Nie ma innego produkcyjnego activation call site. Recovery zachowuje ownera tylko dla exact `ACTIVE/sessionId/target`, w przeciwnym razie go zwalnia (`AniyomiLoadBoundary.kt:516-540`). Test blokuje recovery read i potwierdza, że activation czeka, po czym odzyskuje ten sam session ID bez drugiego loadera (`AniyomiLoadBoundaryTest.kt:487-557`). Poprzedni startup P1 jest zamknięty.

Factory construction wiąże worker TCCL z owned loaderem i przywraca poprzedni w `finally` (`AniyomiLoadBoundary.kt:248-255`). Realna klasa fixture wymaga tego loadera i próbuje wczytać `FoxTvApplication` przez caller loader oraz TCCL (`AniyomiLoadBoundaryTestFixtures.kt:169-184`). Poprzedni ambient-TCCL P2 jest zamknięty dla obecnej granicy wykonania M3.

## M2 pinning nie konsumuje M3 rollback authorization

**[P2][confirmed]** `rollbackAfterFailedActivation` pobiera failed/LKG pair przez `boundary.rollbackRequest()` pod M3, po czym zwalnia mutex przed wejściem do lifecycle (`AniyomiLoadBoundary.kt:641-651`). Lifecycle zdobywa M2, ale sprawdza request wyłącznie względem M2 `selected` i `previous`; nie potwierdza ponownie enabled-idle ani failed/LKG w M3 (`AniyomiLifecycleCoordinator.kt:84-129`).

```text
rollback R: M3 read request(F,G) ---- pause ---- M2 validates F/G -> swap G -> activate G
retry T:                                M2 -> M3 activates F successfully
```

Retry nie zmienia M2, więc R zwalnia świeżo udaną sesję F i cofa ją do G. Jeśli w lukę wejdzie `disable()`, R nadal zmienia durable M2 pointer na G, a activation dopiero potem zwraca `DISABLED`. Deklarowane „consume” nie występuje.

Test updater-vs-rollback potwierdza poprawne M2 pinning od chwili wejścia lifecycle (`AniyomiLoadBoundaryTest.kt:404-484`), ale nie obejmuje operacji M3-only. Po zdobyciu M2 trzeba ponownie zwalidować i atomowo zająć exact M3 pair, blokując retry/disable do końca swap+activation, oraz dodać deterministyczne testy retry-wins i disable-wins.

## Legacy API 24–25 workspace kontra ART od API 26

Oficjalne `android-37.0/dalvik/system/DexClassLoader.java` wymaga prywatnego writable directory przed API 26 i określa `optimizedDirectory` jako niemający efektu od API 26. Kod nazywa argument `legacyOptimizedDirectory`, opisuje realne zapisy tylko na API 24–25 i na nowszych wersjach traktuje katalog jako własny marker/workspace bez roszczenia do ART (`AniyomiLoadBoundaryModels.kt:314-321`; `AniyomiLoadBoundaryStorage.kt:204-206`). Przekazanie go pozostaje potrzebne dla minSdk 24; platforma ignoruje go na API 26+.

**[P3][confirmed]** `LOAD_BOUNDARY_DESIGN.md` nadal deklaruje „generation-specific optimized-code cache ownership”, usuwanie „optimized output” i „optimized-code remnants” (`:63,115-123,163-164,180-182`). Należy opisać legacy workspace z API 24–25 oraz platform-managed ART od API 26. Kodowa część poprzedniego P2 jest zamknięta; drift dokumentacji jest non-blocking.

## Test gate i niezmieniony journal cut-point gap

Świeże, zawężone `:app:testDebugUnitTest` dla boundary, boundary storage, lifecycle storage i packaging zakończyło się `BUILD SUCCESSFUL`: 42 testy, 0 failures. Obejmuje same-SHA/different-policy, updater czekający na rollback oraz activation czekające na startup recovery; nie obejmuje stale retry/disable ani Android ART/device.

**[P3][confirmed]** `AniyomiLoadBoundaryStorageTest` nadal ręcznie tworzy jeden układ `base + .bak + .next` (`:16-39`), a state store nie ma fault-injectable seam dla rename/delete/restore w `write`, `settleInterruptedWrite` i `rollbackWrite` (`AniyomiLoadBoundaryStorage.kt:49-162`). Status: **OPEN, NON-BLOCKING, bez regresji, bez cut-point fault-injection coverage**.
